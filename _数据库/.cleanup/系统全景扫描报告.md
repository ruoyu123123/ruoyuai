## 🚨 四、识别的问题（按严重度排序）

### P0 - 严重影响 AI 驱动体验
1. **核心流水线日志噪音** (245 处 print)
   - orchestrator 已修复，但 gen_writer/save_state 等下游仍噪音
   - GUI 模式时日志混乱到无法解析
   - SILENT 模式无效（下游脚本不受控）

2. **没有统一的日志级别控制**
   - RUOYU_LOG_LEVEL 环境变量未被脚本读取
   - 每个脚本自己决定输出什么
   - 调试时无法动态开启 DEBUG

3. **结构化输出缺失**
   - JSON 输出和文本日志混在一起
   - orchestrator 需要解析脚本 stdout，但格式不统一
   - GUI 进度条无法精确解析进度

### P1 - 影响开发效率
4. **测试基础设施不完善**
   - 301 个测试文件存在，但**未运行覆盖率统计**
   - 不知道哪些核心逻辑缺测试
   - 改代码后不敢确认没破坏其他功能

5. **技术债少但分散**
   - 仅 9 处 TODO/FIXME 标记（说明要么很干净，要么标记不全）
   - 需要扫描 `# FIXME` / `# TODO` / `# XXX` / `# HACK` 确认

6. **文档与代码不同步风险**
   - 68,903 行代码 vs 3,822 行经验文档
   - 经验文档是代码的 5.5%（偏低，说明很多逻辑没文档化）
   - STRUCTURE.md 提到的 34 子系统 JSON，实际是否全部实现？

### P2 - 长期优化
7. **CLI 入口过多** (124 个)
   - 很多脚本既是库也是 CLI
   - 没有统一的 CLI 规范（argparse 为主，但格式各异）

8. **异常处理简单**
   - 仅 5 个自定义异常类
   - 大部分脚本直接抛 Exception 或 exit(1)
   - 错误信息不结构化

9. **依赖管理不透明**
   - requirements.txt 存在但未分析内容
   - 不知道有多少外部依赖
   - 没有 lockfile（requirements.txt 没版本锁）

## 📐 六、重构策略（避免返工）

### 渐进式重构原则
1. **核心优先**: 先重构 AI 驱动主路径（orchestrator → gen_writer → save_state）
2. **向后兼容**: log_util 提供便捷函数，降低迁移成本
3. **自动检测**: check_logging_standard.py 持续扫描
4. **分批提交**: 每重构 1-2 个脚本就提交，避免大 PR

### 重构模式（统一模板）
```python
# 旧代码
print(f"[OK] 完成第 {n} 步")
print(f"[ERROR] 失败: {e}", file=sys.stderr)

# 新代码
from log_util import get_logger
logger = get_logger(__name__)

logger.info(f"完成第 {n} 步")
logger.error(f"失败: {e}")
```

### 豁免策略
| 类型 | 是否重构 | 原因 |
|------|---------|------|
| **plan_tracker.py** | 是 | 虽是 CLI 但被 orchestrator 调用 |
| **export_book.py** | 否 | 纯用户 CLI，print 是功能 |
| **测试脚本** | 否 | 测试输出不影响生产 |
| **一次性工具** | 视情况 | 如果被主流程调用就改 |
